直答

上一版（v1.12）的限速器修复确认生效 —— 真实帧率从 9.74 跳到 48.3（菜单）/ 24.3（世界），capUs 25641→6289。 这一份收益保住了。

但画面依旧不动。这局把原因量出来了，不是猜的： 我们一直以为自己在读「相机的矩阵」，其实读的是每帧最后一个写这个缓冲的人。 世界里那个写者是一个正交全屏投影（UI / 后处理类 pass）， 它的矩阵永远不变 ⇒ 我们拿它当相机，clipToPrevClip 就恒等于单位阵 ⇒ DLSS-G 判定「相机没动」⇒ 插帧 = 复制上一帧 ⇒ 看起来就是卡死。 v1.13 让「不是相机长相的写入」直接不发布。

二、解剖那个假相机：它是一个正交全屏投影

世界阶段十个字段全部退化成平凡矩阵：

[FLD] #31501 c0  View     row3=(0,0,0,1)          ← 精确的轴交换置换阵 [[0,0,1],[0,1,0],[1,0,0]]
[FLD] #31501 c8  Proj     det=1.11111
[FLD] #31501 c32 PrevVPU  全零
[FLD] #31501 c40 ProjU    det=0.9                 ← 就是上面那个的逆
[RAW] +0x0060 | 0 0 1.111111 -0.1111111 | 0 0 0 1
[RAW] +0x0280 | -464.5398 349.1476 101.2857 0 | 0 0 0 0

把 c8 按 D3D 投影的格式反解：

m22 = zf/(zf-zn)          = 1.111111
m23 = -zn·zf/(zf-zn)      = -0.1111111
m32 = 0,  m33 = 1         ← ★ 没有透视除法 ⇒ 这是 ORTHO，不是相机投影

令 zf=1, zn=0.1，得到 z' = (z-0.1)/0.9 = 1.1111z - 0.1111 —— 与日志里的两个数字逐位吻合。这是一个把 [0.1, 1] 映射到 [0, 1] 的 全屏正交投影，典型的 UI / 后处理 / 阴影类 pass。

三条独立旁证（都不是同一个证据的重复叙述）：

  • CameraPreviousPosAdjust 在世界里恒为 (0,0,0,0) 整整三十秒；在菜单里它紧贴 pos。 一个「上一帧相机位置」不可能是零向量 —— 除非这个结构体根本没被相机写过。
  • m32=0 是结构性判据：真实相机投影必然 m32=1, m33=0（要有透视除法）。
  • 到达率 591/s ÷ 真实帧率 ~24 ≈ 22 次 —— 一个渲染帧里同一个缓冲被 Map/Unmap 二十几次， 而我们（和 Community Shaders）的 hook 都只保留最后一个写者。

三、反证：菜单期的字段是好的，所以不是偏移错

同一局在主菜单的那七分钟，十个字段全是真相机：

观测量菜单期实测说明
path0 → 117.60 单调增长相机在真的移动
prevPos vs pos相差 0.1~0.3逐帧跟着走，不是冻结常量
Proj row3(0,0,1,0) ⇒ m32=1, m33=0透视除法在 ⇒ 真相机
det / mag79.9373 / 15.011手算分解出无穷远投影，zn=15.011

更关键的是：我用手算验证了 ViewProj = Proj · View 精确成立（不是近似）。 ⇒ 字段偏移、矩阵约定、转置方向全都是对的。问题不在「读错了字段」，而在「读错了人」。

四、v1.13 改了什么：唯一一处行为改动

#性质改动
1行为在 AcceptCameraSnapshot 的 usable 检查之后插一道 内容门：
const bool camShaped = |CameraProj[3][2]| >= 0.05 && |CameraProj[3][3]| <= 0.05;
不满足 ⇒ ++snapNonCamera、return false（不发布），并打最多 5 行 [CAM] #N NON-CAMERA write dropped (v1.13)。
2逃生门kCamCaptureFallbackSkips = 6000：若连续 6000 次都不像相机 （说明这个判据本身是错的），自动退回旧行为（接受最后一个写者）⇒ 最坏情况 = 当前版本，不会更糟。
3日志[CAM] pub 行尾追加 cap={}/{} （左边 = 被丢弃的非相机写次数，右边 = 距上次成功捕获的连续跳过数）。

为什么判据是 1 vs 0 而不是估值：两群样本在本局的日志里是精确分离的 ——

|Proj[3][2]||Proj[3][3]|
相机写（菜单，7 分钟）10
假相机写（世界，30 秒）01

阈值 0.05 只是给浮点误差留的余量，两群之间差了整整 1.0。不是猜的，是量出来的。

锁、族指纹、接管、reset-edge 释放 —— 一行都没改。 这是纪律：根因变了，先让新判据单独上机说话， 不要在同一版里叠两个未知。

五、L30（本轮新增的通用铁律）

同一个槽位被多个来源共享时，「谁最后写」不是选源依据。

选源必须用内容里可判定的特征（这里是 m32/m33 的透视除法）， 而且新判据必须带逃生门（这里是 6000 次不匹配就退回旧行为）， 并且先测出两群样本的分离量再写判据 —— 分离量 1.0 和 0.01 是两种完全不同的可信度。

这一条是 framegen-diagnosis 技能的第 53 节，已登记。
