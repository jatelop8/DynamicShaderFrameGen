一、探针的缺陷（铁证在日志里）

v1.14 用一张 8 格的表数「见过的不同位置」。表填满之后既不淘汰、也不再写入， 但计数照样加 —— 于是它实际数的是「与最初那 8 个位置相差超过 1 单位」的到达次数。

[CAM] WRITER #9  NEW pos=(-49.995,892.661,95.364) prevPos=(-49.996,893.077,95.400) arr#3645
[CAM] WRITER #10 NEW pos=(-49.995,892.661,95.364) prevPos=(-49.996,893.077,95.400) arr#3648

两条记录的 pos 与 prevPos 逐位相同，却都判为 NEW —— 说明表里装的是更早的 8 个值。一个完全停住的写者，也能让这个计数器无限增长。

L31：数「见过几个不同的 X」之前，先定义「X 的表满了怎么办」。

不设上限的「新值计数」，把从未见过和在变化混为一谈。 这与 L28（用一个会被故障自己重置的计数器做门）是同一族错误的两端。

三、接管门死锁（确证）

v1.11 的接管门（FrameGen.cpp:1143）要两个条件同时成立：

if (snapPubStale >= kCamPubStaleTol(200) && snapForeignMove >= kCamForeignMoveTol(200))
条件阈值世界段实测结论
snapPubStale20080，每秒 +26 需要 7.7 秒，世界段只 3.4 秒
snapForeignMove200恒 0 被拒族位置恒定 ⇒ 步长 0 ⇒ 永不累计

第二个条件是结构性的：它只在「被拒的族自己在走」时才增长。而世界里被拒的是 停着的菜单相机，所以它永远不会满足。

这个死锁是安全的 —— 它不会让菜单相机夺流，所以一直没暴露。

四、v1.15 改了什么（纯诊断，零行为改动）

  • 删掉旧 census，换成按族测位移：16 个族槽，每槽记 (proj00, lastPos, moved, stepSum)，比较相邻两次到达的步长， 超过 0.05 才计一次「在动」。
  • 每秒一条 [CAM] FAM[n] proj00=… moved=… stepSum=…。
  • family rejected 行：pos 精度从 1 位小数改 4 位，并加上 prevPos 与 row3 —— 1 位小数下「停着」和「在滑」看不出区别， 这正是上面那张表读不准的原因。
  • [CAM] MOTION fam=… step=… 打印前 60 次真实位移。
  • 族表满时打印告警而不是静默丢弃（被丢的那个族很可能就是活相机）。
