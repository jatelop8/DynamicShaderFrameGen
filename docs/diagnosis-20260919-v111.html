v1.11 — 「门」被它要检测的故障本身清零

2026-09-19 14:20 那局 · 日志 653,545 B · DLL md5 75e38aa7… · commit dbf278f · tag v1.11

一、直答

1. 是「卡死」吗？

不是。watchdog 最后一行为 alive=1、帧号仍在涨、presentAge=102ms —— 进程活着。真实帧率掉到 ~10 fps，而且画面完全静止， 所以体感和卡死一样。

2. 4x 和 DLSS5 同时在跑吗？

都在跑。DLSSNR CHAINED with frame generation 出现； hwMax=6 ask=4 accepted=4；世界中每次 present 各出 4 个 flip。

3. 那为什么画面不动？

因为插进去的 3 帧和上一帧一模一样。发布给 DLSS-G 的相机被冻结在一台 场景固定的假相机上（pos=(-243.05,-415.31,118.56)）， 于是 clipToPrevClip = 单位阵 ⇒ DLSS-G 认为「相机没动」⇒ 复制上一帧。

4. 找到根因了吗？

找到了，而且是代码层可复现地推出来的： v1.10 的接管门的计数器 snapLockStill， 被它要检测的那个故障自己清零，所以门永远打不开。

三、根因：门被故障清零

v1.10 的接管条件写的是 snapLockStill >= 30。而 snapLockStill 在每一次 accept 时都被置 0：

FrameGen.cpp:1073   } else { snapLockStill = 0; }     // `continues` 分支
FrameGen.cpp:1069   snapLockStill = 0;                // same-family step break
FrameGen.cpp: 933   snapLockStill = 0;                // acquire

冻结的假相机以 d2 == 0 到达自己的上一个到达点 ⇒ continues 为真 ⇒ 被接受 ⇒ 计数归零。

实测印证：still 全程只在 3 ~ 8 之间徘徊， 而 famRej 涨到 34681。门永远打不开。

唯一那次成功接管能触发，是因为一次 release 刚把 snapHaveLast 清掉；而它证明了机制本身有效 —— matChanges 3 秒内从 2 冲到 542。

四、v1.11 改了什么：只有一处行为改动

位置改动
FrameGen.h 新增 std::uint64_t snapPubStale = 0; —— 连续多少次发布出去的矩阵逐字节相同
发布点 if (!same) { ++snapMatChanges; snapPubStale = 0; } else { ++snapPubStale; } —— 全文唯一的清零点，落在「矩阵真的变了」这一健康分支上
常数 kCamForeignMinRej = 30 → kCamPubStaleTol = 200 （200 ≈ 1.3 秒的可证死发布流）
接管门 改为 snapPubStale >= kCamPubStaleTol && snapForeignMove >= 200 —— 第二条件一个字没动
心跳 [CAM] pub … fMove={} takeover={} stalePub={} | {}； stalePub 超阈时 verdict 直接写 「the published camera has been byte-identical for a long run」

为什么第二条件不能改：它才是安全性的来源。停住的族贡献不了位移， 所以「玩家本来就站着不动」（此时单位阵的 clipToPrev 是对的）永远夺不走 anchor。

没做什么：锁状态机、族指纹、release 路径、step-break 逻辑一行未改。

七、诚实边界

  • 「为什么接管前会锁到那台假相机」仍未证。v1.11 只保证锁能自愈（~1.3 秒内）， 不解释它怎么锁错的。
  • 世界内 10 fps 的成因未证。嫌疑：RenderResolutionScale=0.44 （渲染 1689×950）而 NRRenderScale=1.00 ⇒ 每个真实帧做一遍 3840×2160 的 DLSS5 神经渲染。没测过，改一个 INI 值就能界定 —— 代价是 DLSS5 清晰度， 要不要试由你定。
