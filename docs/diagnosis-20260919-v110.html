直答你的直觉对：画面没变顺。但机制不是「4x 没插帧」—— 4x 真的插了，只是插进去的 3 帧和上一帧一模一样。
而且这一局终于把根因量出来了：锁拿着一个场景固定的相机（菜单/载入相机），真正的玩家相机被当"异族"全部拒掉。 v1.09 加的探针就是为这件事加的，它一次就给出了答案。

一、这局实测到的三件事

accepted=44x 被运行时接受（测量值，不是推算）
hwMax=6运行时自报支持 6x（5 个插帧）
clipDev=0.000061重投影矩阵 = 单位阵 ⇒ 相机被当成没动
matChanges 冻结 1689.2 秒 / ≈2100 次发布，矩阵逐字节没变
1. 4x 从来没有被上限卡住。

prev == cur（位置、矩阵都相同）⇒ clipToPrevClip = inv(cur)×prev = I ⇒ DLSS-G 被告知"相机没动" ⇒ 每 4 个呈现帧里 3 个是同一张图。

这就是 v1.09 那一行探针存在的全部理由 —— 之前 19 288 次逐字节相同的发布，在旧日志里看起来像"很健康的忙碌捕获层"。

二、根因：锁拿着「场景固定的相机」，真相机被拒

判据不是估值，是跨运行的数字逐位恒等。
  • 被锁住的位置 (-243.05,-415.31,118.56)，与 Streamline.cpp 的 v1.07c 注释里引用的 23:10 那局（两天前）cameraPos=(-243.049301,-415.311523,118.558205)、 clipToPrev[3].w=-195.222366 —— 逐位相同。
  • 活着的相机不可能精确复现另一局的坐标 ⇒ 那组值是场景几何（3D 菜单 / 载入画面相机）。
而真正的活相机以 proj00=1 到达，位置在走，却被当"异族"全拒： 
[CAM] #67695 family rejected: proj00=1 locked=0.8391 ratio=1.1918 pos=(-125.7,210.8,188.4) dist=640.8
[CAM] #69020 family rejected: proj00=1 locked=0.8391 ratio=1.1918 pos=(255.0,804.7,-94.4)  dist=1334.8
反证：菜单阶段同一个 proj00=1 在 pos=(-160.0,160.0,128.0) 上逐字节恒定（238 条拒绝全同） ⇒ 它的行为与"活相机"完全一致：菜单里静止、世界里走动。
触发点 —— 我把锁交给了一个假设"下一个到达一定是世界相机"的地方： 
11:33:15.482  [CAM] #66564 lock RELEASED on the reset edge (was proj00=0.149184 famRej=13575)
                      - the next arrival re-acquires
11:33:15.482  [CAM] pub #52989 ... proj00=0.8391        <-- 下一个到达 = 场景固定的那种
v1.07b 的注释自己写着 release 之后 "hands the lock to the first arrival after it, which is the world camera whenever the menu has closed" —— 这条假设是错的。

而且放不掉： 
[CAM] #66488 family rejected: ... still=1570/90
连续 1570 次拒绝、阈值 90、什么都没发生。全程 lock RELEASED 只有 3 条，全是 on the reset edge。

三、我自己读错的两处（写下来，避免再犯）

看起来像缺陷读代码后
[MFG] debug CHECK: ... blocked=396 unblocked=1
我第一遍读成"我们跳过了 396 次 SetDLSSGOptions"		 不是缺陷。DX12SwapChain.cpp:1372-1439：blocked/unblocked 数的是 menuBlock，即菜单守卫帧数。396 = 菜单开着 396 帧；警告之所以打， 是因为唯一那一个非菜单帧的 EvaluateDLSSG 返回了 false。
camPrev(ok/used)=1/90
我第一遍读成"90 次里只成功 1 次"		 不是缺陷。Streamline.cpp:1002 是 diag.camPrevOk = camPrevOk ? 1 : 0; —— 赋值，瞬时标志； 只有 camPrevUsed 才是累加。它读作"此刻重建成功，且已被使用 90 次"。

四、v1.10 改了什么（已构建 = 已部署）

  • 核心（一处行为改动）：!sameFamily 分支尾部不再无条件 return false。 它现在累计被拒族自己的位移；当 still ≥ 30 且位移 ≥ 200 单位（kCamForeignMoveTol）时， 由这个会动的族接管 anchor。
  • 为什么这不是 v1.07b 删掉的那个 v0.94 re-acquire：v0.94 是"谁排在第 90 个谁赢"（只看顺序）， 所以一个静止的错族也能靠顺序夺锁（v1.07b 注释说它有一半概率落到 proj00=1）。 这里被拒族必须自己走出 ≥200 单位才可能接管 —— 静止或陈旧的相机不可能满足。计数下限只防抖动。
  • 顺带修掉我自己的一个真 bug：main.cpp 里 WatchdogLogPath() 的缓冲区由 InitWatchdogLogPath() 填充，而 v1.09 把归档调用写在了它之前 ⇒ 缓冲区为空 ⇒ 11:30 那局一个归档文件都没有，DynamicShaderFrameGen.20*.log = 0。已调正顺序。
  • 新增读数：[CAM] pub 增加 fMove=（被拒族累计位移）与 takeover=（接管次数）。
