DynamicShaderFrameGen · v1.07b · 2026-09-18

为什么需要这一趟

22:02 那份日志里，被发布给 DLSS-G 的相机原地不动（逐帧位移 move=0.0000， 位置在 1e-2 精度下几十秒不变），于是 clipToPrev = I，生成的帧是当前帧的副本 —— 画面不可能前进。

但 move=0.0000 只有在玩家在走的时候才是错误。那份日志里玩家几乎没动， 所以它没有回答最关键的问题。缺的是一个数据点，不是又一个猜想。

项目里早就埋了这条探针，注释原文就是为这一刻写的：
“若玩家在走而这里 move/path 恒为 0.000，则根因在捕获层（读到的相机数据不跟踪真实相机）， 任何重投影侧的修法都救不了。”

要做的两件事

  1. 进游戏 → 等 4x 跑起来（左上角帧数明显高于实帧）→ 按住 W 往前走约 10 秒，同时转视角 → 退出。
  2. 在工程目录跑：
    python tools/analyze_session.py
    它会先核对横幅是不是 v1.07b。不是的话后面都不作数。

三条判据 —— 看到哪个，根因就是哪个

判据日志里看到根因下一步查哪里
A move 明显非 0，且心跳 clipDev 明显 > 0 相机链是好的 冻结在呈现 / 配速侧（pacer、Present 环绕）。转去查那一条，与相机无关
B 在走，但 move≈0、path≈0 捕获层读到的相机不跟玩家 perFrame 镜像的偏移 / 布局。线索已经在那儿了：ProjUnj[3][3]=0.0667（真投影应为 0）、 ViewProjUnj 的 w 行不是 [0,0,0,1]、detProj=0
C move 大，但 clipToPrev≈I 重建 / 历史环节把运动丢掉了 rebuildViewProj（Streamline.cpp:629）与 s_prevVP 推进 （1022-1050）

三种结果对应三个不同的根因，每种都直接指向一个具体例程，不需要再猜。
