直答

画面动不了，不是因为相机冻住，是因为游戏真的只跑 10 帧。 v1.11 的接管其实成功了 —— 它触发后 clipToPrevClip 就不再是单位阵。 但真实帧率被限速器压在 9.74 fps，四倍帧生成把 4 个呈现帧摊在 102 ms 上， 每个插帧要跨越 100 ms 的世界运动去重投影，看起来就是"卡住、动不了"。 本次修的是这个节流，一行公式。

一、这局实测到的四件事

#事实日志原文
1v1.11 的接管真的触发了（这是第一次门开了） #5507 FOREIGN TAKEOVER (v1.11): locked proj00=0.8391 has gone 211 publishes with an unchanged matrix while the refused family proj00=1 travelled 353.9 units - adopting pos=(-865.8,657.2,285.8)
2接管后重投影有运动了：clipDev 从恒定 0.000061 变成 0.011~0.547 摆动；非仿射告警停止增长 [MOTION] clipToPrevClip[3].w=167.815231（14:56:04.765，最后一次）之后 clipW=1.000000

二、根因：限速器的量子被作用在 flip 上

src/Streamline.cpp → ReflexSleep()：

const double want = Get().refreshRate / static_cast<double>(capMult) - 1.0;   // ← 就是这个除法
capFps = ...;                      // 160 / 4 - 1 = 39
opts.frameLimitUs = 1000000/39;    // = 25641 us

frameLimitUs 是每个上屏 flip 的量子：39 flip/s。而每真实帧要发 4 个 flip， 于是渲染侧被压成 39 / 4 = 9.75 fps。这个量子不是 GPU 算得慢，是一道人为的闸。

三、四项独立印证（同一份日志，全部复现 1e6/(160/capMult−1)）

观测日志值反推
capUs（倍数还是 2 时）126581e6/(160/2−1) = 1e6/79 ✓
capUs（倍数变 4 之后）256411e6/(160/4−1) = 1e6/39 ✓
真实帧间隔 dt102.56 ms4 × 25641 us = 102564 us ✓ 五位有效数字
真实帧率（watchdog 复核）9.74 fps39/4 = 9.75 ✓
菜单里的 real39.0菜单 1 flip/帧 ⇒ 39/1 ✓（GPU 受限不会恰好压在 39.0）

★ 判据「钉死 vs 飘动」：限速器的量子是平的（dt 离散度只有 0.02 ms）； GPU 真的算不动时，帧间隔会飘几毫秒。这一局是钉死。

四、为什么前面几轮没找到：文件里两段注释互相矛盾

Streamline.cpp 的 v0.63 注释把这个根因诊断得完全正确：

// v0.54 按"渲染帧率"反推（刷新率 / 总倍数 - 1），等于把 flip 节流到 39/s；
// 而 DLSS-G 每真实帧要发 4 个 flip ⇒ 渲染侧被压成 39/4 = 9.75fps。
// 实测 102.56 / 25.641 = 4.0000（5 位有效数字）...
// 现在：cap = 刷新率 - 1 ... 倍率不再参与上限计算。

而紧下面的 v1.06 注释把同一行改了回去，理由是"去掉除数是 636 present fps ⇒ 21:27 冻结"。 那个推理把 flip 上限当成了渲染上限 —— 而本局的实测（dt 正好是 4 倍量子、real = capFps/4） 证明它是 flip 上限。执行的是 v1.06 那一版。

⇒ L29：同一个函数里两段互相矛盾的注释，本身就是"这里被改坏过"的信号。 判据不是哪段更新，而是哪段能被测量证实。

五、v1.12 改了什么

#性质改动
1行为want = Get().refreshRate - 1.0; 去掉 /capMult ⇒ capFps=159、frameLimitUs=6289（与工程内既有注释 capUs=6289 一致）。 flip 节流在 159/s < 160 Hz，渲染侧 159/4 ≈ 39.75 fps。
2断言capFps * capMult > refreshRate 是 v1.06 的误读，改为 capFps > refreshRate（flip 上限不能超面板），并新增一行 Reflex cap check (v1.12): … = … rendered fps at …x。
3日志Reflex FLIP cap 行不再打印 capFps * capMult （那会印出 636 假超发），改为 ~… presented fps, ~… rendered fps (v1.12: the cap is the FLIP rate)。

安全性：capMult=1（不用多倍帧生成）时，改动前后都是 159 ⇒ 行为不变。

逃生门：INI 的 ReflexFpsLimit 优先级高于公式。若这一版反而更糟， 把 ReflexFpsLimit=40 写进 INI 即可精确退回今天的行为，不用换 DLL。

锁、族指纹、接管逻辑一行未改 —— 真实帧率变成 4 倍后接受的节拍整体改变， 必须先在新节拍下重测，再决定要不要碰锁。这是纪律，不是回避。
