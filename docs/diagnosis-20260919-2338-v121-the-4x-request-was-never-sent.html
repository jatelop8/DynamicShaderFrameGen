上一轮我只改了 INI 三行（Provider 1→0、MFGMaxFramesOverride 3→0、 NRAllowWithFrameGen 0→1），把配置退回到「FSR3 两倍帧生成 + DLSS5」——你自己说过已经做到过的那一套。 你说「画面活了」。于是三个提供者状态终于可以并排看了：

结论：冻结是 DLSS-G 这条支线独有的，不是「帧生成」这件事本身的属性。 上一轮的头号嫌疑（NR ↔ DLSS-G 串联）和「引擎半死 / 游戏暂停」两条线，到这里一起封棺。

你那句「只有 60 帧、双倍都没有了」也在这份日志里找到了出处。这是这一局的关键数字：

[FrameGen]  FPS probe: real=27.8 | FSR3 | cap~=55.6 (=real*2, COMPUTED not measured)

  • numGeneratedFrames=1 是 FSR3 后端自己填的（我们只读不写，FidelityFX.cpp:121-136 的注释就是为这件事写的） ⇒ FSR3 的天花板就是 2x，这是 API 事实，不是 bug。
  • 右上角那个数字 = 真实帧率 × 倍数。FSR3 路上倍数被硬编码成 2（ImguiMenu.cpp:204-206） ⇒ 你看到的大约 60 = 真实 30 × 2。数字在翻倍，但基数掉了：NR 以满 4K 每帧跑一遍 + 命令队列饱和 + CPU 背压， 把真实帧率从 ~50 压到了 28。
  • 闪烁的出处也在这里：NRAllowWithFrameGen=0 那一局根本没被读到（见第三节）， 所以 DLSS5 和插帧在 FSR3 路上无条件叠在一起 —— 两个时序处理器为同一帧写历史，这是项目里记了很久的闪烁源。

二、4x 没出现，因为我们一帧都没往 DLSS-G 递

这是本轮最重要的发现，证据全部来自 22:54 那一局自己的日志。四行放在一起读：

[22:54:56.062] [MFG] stall governor: frame took 346 ms ... step held at 4x, accepted 4x
[22:55:04.060] [MFG] probe edge: menu guard released, SetDLSSGOptions resumes on this frame
[22:55:04.060] [MFG] debug CHECK: Present skips SetDLSSGOptions even though the menu guard is
               not engaged (menuBlock=0 frames=0 blocked=571 unblocked=1)
[22:55:04.324] [Streamline] DLSSG presented per real frame = 4 (status=0)
  • blocked=571 / unblocked=1 ⇒ 菜单闸门在 572 帧里真了 571 帧。 那条 if 链（DX12SwapChain.cpp:1413-1429）在闸门为真时既不调 SetDLSSGOptions 也不调 EvaluateDLSSG。
  • 于是全程 presented per real frame = 1 —— 一个插帧都没有。
  • 闸门一放开，0.3 秒后同一份日报告诉我们「4」。 因果就写在这一行里： 4x 的请求不是被运行时拒绝的，是从来没被发出去。
  • 你上一轮说的「四倍帧生成感觉也没成功」——在那一局里是准确的。

那到底是什么菜单？22:54 的菜单探针说得很清楚：

[XRAY] MENU PROBE ... IsMenuOpen(is)=false/false/false  IsMenuOpen(literal)=false/false/false
[XRAY] MENU EDGE open=1 serial=2   presentedBefore=0
[XRAY] MENU EDGE open=0 serial=573

serial 2 那一刻，所有真实菜单都是关的，而闸门是开的。菜单判定里唯一还能成立的就是最后那一项 IsMenuOpen("Fader Menu")（Streamline.cpp:386-405）。而这一局（23:38）新加的见证证明 淡出菜单在玩家位于世界时是常开的：fade=1 连续 40+ 秒，同时 paused=0 ld=0， 而你肯定在世界里（我让你站了 15 秒）。

⇒ MenuDisableFrameGen=1 加上「把淡出菜单当菜单」= 在世界里闸门永久为真 = DLSS-G 永远拿不到帧。

为什么不直接把 Fader Menu 删掉：账本 v0.96 记着删掉它进不去游戏（已回退）。 探针解释了为什么 —— 它就是启动期的唯一保护（serial 2 只有它在开）。 所以这一版的规则是：淡出菜单只在「我们还不该在世界里」时算菜单（Loading Menu 开着，或进程前 90 秒）， 真实菜单（Main / Loading / Journal / Pause / RaceSex）照旧照算。

三、第二条机制：v0.75 拆掉的那道跨 API 围栏

同一天 22:54 的看门狗，每 0.2 秒一条：

22:55:04.415  frames=581  ...  lastPr=584
22:55:04.616  frames=586  ...  lastPr=604     <-- 从这里开始分叉
22:55:05.017  frames=597  ...  lastPr=648
22:55:06.858  frames=643  ...  lastPr=832     <-- 68 个真实帧，多了 190 次 present
              dsync=0（全程）
  • lastPr 是 DXGI 自己的 present 计数，frames 是我们的真实帧计数。差值 2.5 秒内从 3 长到 189 ⇒ 4x 真的在上屏（dsync=0 说明后缓冲索引在推进）。可是画面不动 ⇒ 推的是同一张内容。
  • DX12SwapChain.cpp:1289：static constexpr bool kD3D12WaitsOnD3D11 = false; —— 这是 v0.75 拆掉的。被拆掉的是 d3d11 Signal + d3d12 queue Wait。
  • 拆它的理由是「07:11 那局 fence 50 秒停在初值 1」。而没有 Signal 的 fence 看上去就是这样。
  • 代价：D3D12 队列读 swapChainBufferWrapped / colorOutWrapped（都是 D3D11 写的）时 没有任何定序，而 DX12SwapChain.cpp:1248-1250 的注释至今还写着「必须在 fence 之前（D3D11 写 colorOut 完成后随 Signal/Wait 同步，D3D12 拷贝才能稳定读到）」—— 同一条注释依赖的定序，被 v0.75 拿掉了。
  • 更要紧的是 v0.75 自己的注释写着：「doodlum 的 ENBFrameGeneration 保留了这个双向等待并且工作正常…… 把它当成待否证的假设，而不是从可用参照移植来的做法。」现在有证据可以否证了。
