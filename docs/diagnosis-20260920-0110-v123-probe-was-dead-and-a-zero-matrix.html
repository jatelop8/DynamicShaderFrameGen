一、先回答你的问题：问题出在三个地方，其中一个是我上一版自己写坏的

我的 BUG

v1.22 装的像素探针，39 秒里一个样本都没采到 —— 而它是唯一能回答「画面到底动没动」的仪器。 日志里只有一行 [PIXEL] probe armed（00:58:14.810），之后再无下文。

根因在我自己的代码里：CopySubresourceRegion 和 Map 写在同一次调用里， 所以 Map 永远在问一张 GPU 还没写完的纹理，恒返回 DXGI_ERROR_WAS_STILL_DRAWING； 而那条失败分支还写了 pixelProbeLastMs = 0，把 1 Hz 节流废掉， 于是每一帧都重试一次、每一帧都失败、一句日志都不打。

两个后果：① 这一局最需要的数据没有；② 它把一次跨 API 拷贝塞进了每一帧 （从 D3D12 拥有的共享后备缓冲拷到 D3D11 staging）—— 这是 v1.22 里唯一改动渲染热路径的东西。

真缺陷

一个「零矩阵」被当成了合法的 clipToPrevClip，还被写进历史，之后反复重放。

[W] [MOTION] clipToPrevClip[3].w=-68.073540 (must be 1) ... v1.08 PROBE:
    p00 cur=6.7031 prev=0.0000 | p23 cur=-15.010994 prev=0.000000
[FLD] #1 c32 PrevVPU row3=(0,0,0,0) [3][3]=0 dev=1 det=0 mag=0 BAD

prev 全是 0 ⇒ inv(cur) x 0 = 0。而代码里唯一的合法性判据是 clipMagAll < 1.0e30f（本意是挡 NaN/Inf）—— 零矩阵的 mag 是 0，「小于 1e30」完全成立， 所以它被接受，并且被存进 s_lastGoodClip，也就是后续帧回退用的那份「上一帧合法位移」。 污染是不可逆的。

而且它在 clipDev 那一侧更会骗人：零矩阵的 max|I - 0| = 1.0， 看起来像「相机动了很远」，实际是个退化矩阵。

诊断自伤

我这轮被自己写的两条诊断误导了。

  • 判定链把 tidCallsB > 10（「第二个线程在持续调用 slSetConstants」）排在所有检查之前， 可是日志显示 a=1 —— 第一个调用者只调了一次就再没回来（世界入口处的一次性调用）， b=30→180 只是渲染线程正常每帧调用。它一条危害都证明不了。
  • - depth/mvec must read 2560x1440 (the real interop buffers) 打印时， 三个 extent 全是 3840x2160；而这些 extent 就在上面几行从 interop 资源本身读出来 （v0.56 正是为修那个 1.5 倍错配才改成从资源取）。这条陈旧断言确实短暂地把我引向 「分辨率不匹配」这个不存在的方向。

六、下一局请这样跑（协议改了，第二步必须够长）

① 进世界站着不动 15 秒 → ② 按住 W 走 10 秒以上 → ③ 再退。

为什么第二步要 10 秒：探针报 VERDICT 需要连续 10 个样本，而且要求其中 ≥5 个样本相机在动。 走 5 秒只会得到「站桩」判定，等于白跑。

  • 本轮修的是仪器 + 一个已证的缺陷，没有证明冻结已经消失。它到底修没修好，只有你跑完这一局才知道。
